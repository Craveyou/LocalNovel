### LIVE-01：业务限流被错误包装为500

对全新测试身份的同一空书籍键执行正常 JSON `{}` 单书删除，前10次返回204，第11次起返回500 `INTERNAL_ERROR`，而契约要求429 `RATE_LIMITED`。v1/v2均复现，非文件解析或数据库迁移失败。用于定位的线上 requestId：`a69d3f56-4558-4ec3-8ded-715de1b3186e`、`cd5a04a9-2daa-4ee2-bbcd-2fcb577bbc26`。

源码原因：`@fastify/rate-limit` 在超限时抛出 `errorResponseBuilder` 的返回值；当前返回普通错误信封，没有 `statusCode`，统一错误处理器的429分支无法识别，落到500。应保持限流阈值与协议，修正错误类型/状态传递并添加真实 HTTP 限流回归，不放宽阈值或只调整客户端提示。

已移除错误的自定义 builder，保留插件标准 Error/statusCode，由既有统一处理器生成429信封与 Retry-After。新增 v1/v2 HTTP 注入回归，修复前2项均实测500失败，修复后完整Backend90/90通过（含18项临时PG17），lint/typecheck/build通过。原失败日志 `/private/tmp/xlib-live-rate-regression-before.log`，修复后 `/private/tmp/xlib-live-backend-fix-postgres.log`。服务器未部署此修复，线上第11次仍应按实际响应记失败，不能以本地绿灯替代。

首轮12文档功能全部通过，但集中清理超过删除限额，整项因此失败，不能写成整轮通过。后续清理分配到本轮设备的独立配额，并增加独立第11次边界断言。

第二轮原生套件（`ios-20261025-222110-61848.xcresult`）中，20秒调度和身份/TXT仲裁两项通过；边界测试仍收到500，多文档第11次删除也在60秒窗口内触发相同限额，两个用例失败（4处断言），本轮清理无失败。正常多文档用例已增加第10次删除后的60秒等待，不提高服务器限额；逐样本日志改为依据 XCTest 失败数输出 PASS/FAIL，避免继续清理时误打印通过。边界测试仍独立保留429断言。

限流节奏修正后，12个文档全部通过，最终精确单书清理及设备撤销无失败；这消除了正向测试自身的配额冲突，不代表服务器的500已修复。

### LIVE-02：iOS重进设备管理后，已撤销设备重新出现

真实 UI 点击移除后，该行先消失；返回上一页再进入设备管理，已撤销设备又带“移除”按钮出现。线上鉴权仍正确拒绝该设备403，因此不是服务撤销失效，而是 iOS 设备模型未消费 `revokedAtMs`，重新拉取列表时将撤销历史当成活动设备。

结果包同上：设置自动保存与20秒重登记、初次移除及403断言完成，重进列表断言失败；该用例78.098秒。应由客户端区分活动与历史设备，不删除服务器历史来掩盖展示问题。

iOS源码已增加可选 `revokedAtMs` 解码并在 `loadDevices` 过滤撤销历史，旧进度/凭据设备快照无该字段时仍可解码；新增连续两次拉取的模型回归已通过。修复后的真实UI复验通过（68.527秒）：配置自动保存、20秒自动重登记、移除后重进列表不再出现、被撤销设备403均完成。不改Backend列表语义或历史数据。
