# txt 为什么会乱码

## 一句话

txt **不是一种格式，只是一串字节**。它没有文件头，也没有统一的编码标记——
同一份文字用 UTF-8 存、用 GBK 存、用 Big5 存，得到的字节完全不同。
用错编码去解，程序不会报错，只会把每两个字节当成一个别的字，于是整篇变成"看不懂的字"。

> 类比：同一段话，一个人用拼音写、一个人用五笔写，你拿拼音规则去读五笔的字根，就全是乱码。

## 四种常见来源

| 编码 | 谁会产生 | 特征 |
|---|---|---|
| UTF-8 | 网络下载、macOS / Linux、现代编辑器 | 常见字 3 字节；有 BOM 时开头 `EF BB BF` |
| GBK / GB18030 | Windows 记事本（默认）、老网站、中文论坛 | 常见字 2 字节；无标记 |
| Big5 | 港台来源的繁体书 | 2 字节，码位范围与 GBK 重叠 |
| UTF-16 | 记事本「另存为 → Unicode」 | 每字符 2 字节，ASCII 会夹 `00` |

前三种**没有 BOM 时只能靠猜**，而且 GBK 与 Big5 的字节范围大量重叠——同一个字节序列在两边都是"合法汉字"，只是意思完全不同。

## App 现在怎么判断（2.8 起）

按顺序，前一步确定就不再看后面：

1. **BOM**：文件自己声明的编码，最可信（UTF-8 / UTF-16 LE / UTF-16 BE）。
2. **UTF-8 严格解码**：Foundation 遇到非法字节直接返回 nil，不会悄悄替换，所以能通过就是对的。
3. **UTF-16 必须有特征才试**：这是之前「有的 txt 乱码」的根因——
   UTF-16 几乎能"成功"解码任意偶数长度的字节，GBK 文件被它抢先解掉，就成了一屏乱码汉字。
   现在只有在带 BOM，或采样到大量 `00` 字节（英文为主的 UTF-16）时才允许尝试。
4. **GB18030 与 Big5 各解一次，打分取高分**：
   - 常用字命中（"的一是了我不在…"）加分——解对时占比高，解错时几乎不命中；
   - 中文/全角标点加分——解错时 `，。！“”` 会变成生僻字，标点直接消失；
   - CJK 扩展区、私用区、替换符扣分——这些几乎只出现在解错的文本里。
5. 都不行时交给系统探测（Shift_JIS、EUC-KR 等），再不行就明确报"无法识别编码"，不硬凑。

## 还是乱码怎么办

自动判断再准也有边界（很短的片段、GBK 与 Big5 都合法的字节）。这时手动指定一次：

1. 打开这本书；
2. 右上角 **文本编码**（`textformat` 图标）；
3. 选 UTF-8 / 简体（GBK）/ 繁体（Big5）/ UTF-16。

选择**按书记住**（存在 UserDefaults），整本书都生效，重进不用再选。NAS 上的书同样有这个菜单。

判断技巧：

- 全是"锟斤拷"、"烫烫烫" → 多半是 UTF-8 被当 GBK，选 UTF-8；
- 汉字正常但句子读不通、标点全没了 → 多半是 GBK 被当 Big5（或反过来）；
- 字与字之间夹着方块、空格 → 多半是 UTF-16 被当单字节编码，选 UTF-16。

## 已知限制

- **无 BOM 的纯中文 UTF-16**：没有 `00` 特征，会被当成 GBK；手动选 UTF-16 即可（现实中记事本另存 Unicode 一定带 BOM）。
- **同一文件混用两种编码**：无法完美还原，只能按占比多的那种解。
- **GBK 与 Big5 的极短文本**（几十个字、没有标点）：可能判错，手动切一次。
